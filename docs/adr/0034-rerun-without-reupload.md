# ADR-0034 재업로드 없는 재실행 — 클라이언트가 입력 파일을 보존

## 상태

확정 (2026-07-25)

## 배경

Heavy 도구는 결과를 본 뒤 파라미터만 바꿔 다시 실행하려면 매번 원본 파일을 처음부터 재업로드해야 했다. `JobWorker.deleteInputs`가 Job이 DONE/FAILED로 끝나는 즉시 입력 임시파일을 삭제하기 때문이다(`back/src/main/java/com/back/job/service/JobWorker.java:158`). 이 삭제 시점은 106(업로드 한도 레인 차등화)·107(PDFBox 스크래치 메모리)에서 서버 디스크 예산이 이미 빠듯하다는 게 반복 논점이었던 결과라, 백엔드가 결과 확인 후까지 입력을 붙들고 있는 방향은 그 제약과 정면으로 부딪힌다.

## 결정

**입력 파일 보존 책임을 서버가 아니라 클라이언트(브라우저)가 진다.** `FileUploader.vue`는 업로드 성공 후에도 스테이징된 `File` 객체를 메모리에서 비우지 않는다 — 같은 파일을 다시 `FormData`에 담아 재전송할 수 있는 상태를 유지한다. 백엔드 `deleteInputs` 삭제 시점·정책은 전혀 바꾸지 않는다.

- **재실행 어포던스는 기존 "실행" 버튼을 재사용한다.** 현재 스테이징 세트로 이미 한 번 성공했으면 버튼 문구가 "다시 실행"으로 바뀐다(`alreadyRan` 상태, `staged`가 실제로 바뀌는 모든 경로 — 추가·제거·순서 변경·`clear()` — 에서 다시 "실행"으로 되돌아간다). **결과 표시 컴포넌트(`FileResultPanel`/`HeavyJobStatusPanel`)에는 별도의 "다시 실행" 버튼을 추가하지 않았다** — 이 저장소의 Heavy 레이아웃은 파라미터+업로드 패널이 결과와 함께 항상 같은 화면에 떠 있는 2-컬럼 split-view이지, 결과가 뜨면 입력 폼이 사라지는 위저드 흐름이 아니다(`CONTEXT.md` "Heavy 좌:" 서술 참고). "결과 화면에서 다시 실행" 요구는 이미 화면에 떠 있는 좌측 패널의 같은 버튼을 누르는 것으로 그대로 만족되므로, `FileResultPanel`의 기존 관례("초기화는 좌측 업로드 패널의 ✕") — 업로드/재실행 컨트롤을 한 곳에 모으는 것 — 를 그대로 따랐다.
- **초기화(✕) 버튼도 스테이징을 함께 비운다.** 이전에는 업로드 성공 직후 `staged`가 자동으로 비워졌기 때문에 "초기화" 버튼(`ToolPage.resetAll`)이 `staged`를 건드릴 필요가 없었다. 이제 자동으로 비워지지 않으므로, `FileUploader`가 `defineExpose({clear})`로 노출한 메서드를 `resetAll`이 호출해 결과와 함께 완전히 새로 시작할 수 있게 했다.
- **워터마크 등 대상+두 번째 슬롯(다중 파일) 도구도 동일하게 동작한다** — `staged` 배열 전체를 보존하는 방식이라 `PdfWatermarkPage.vue` 같은 소비자는 코드 변경 없이 그대로 재실행을 지원한다.

## 결과 — 알려진 제약

**새로고침·탭 종료 시 메모리에 있던 `File` 참조는 사라진다.** 이 경우 기존과 동일하게 재업로드해야 한다 — 회귀가 아니라 이번 결정에서 감수하기로 한 트레이드오프다(서버 보관은 106/107의 디스크 예산 제약과 충돌). 별도 영속화(IndexedDB 등)는 이번 스코프에 넣지 않았다.
