# ADR-0037 167 부하테스트 측정 환경 — 로컬 개발 + 원격 실측 1회

## 상태

확정 (2026-07-26)

## 배경

167(Heavy 큐 부하테스트)은 절대 처리량(jobs/min)·지연시간 percentile을 측정해 "실제 배포 규모에서 몇 건까지 견디는가"라는 캐파시티 서사를 내는 게 목적이다 — 103(공정성 벤치마크)과 달리 절대 수치가 스코프 안이다(`.scratch/issues/167-heavy-queue-load-test.md`). 원래 설계는 로컬 Docker를 `--cpus=2`로 제한해 운영 Oracle Ampere A1(2 OCPU) 인스턴스에 근접시키는 것이었다(103과 달리 167에만 필요하다고 명시).

이 전제를 그릴링 중 재검토했다: `--cpus`는 코어 **개수**만 제한하지 코어 **속도**(클록·IPC)는 그대로다. macOS Apple Silicon은 Docker Desktop에서도 소프트웨어로 클록을 낮출 방법이 없다. 이 벤치마크가 재는 두 작업(이미지 리사이즈, ffmpeg GIF 변환)은 CPU 연산이 지배적이라, 로컬 절대 수치는 실제 배포 환경보다 낙관적으로 나올 수밖에 없다. 그대로 뒀다면 103이 "로컬 하드웨어와 운영 하드웨어가 달라 절대 수치를 못 믿는다"는 이유로 피했던 함정을 167이 그대로 재현할 뻔했다.

## 결정

**개발은 로컬에서, 최종 측정은 실제 배포 인스턴스(Oracle Ampere A1, 2 OCPU) 1회 실행으로 분리한다.**

- k6 스크립트 로직(비동기 완료 폴링, `Trend` 커스텀 메트릭, admission 임계값 탐색)은 하드웨어와 무관하므로 로컬에서 빠르게 반복하며 개발·디버그한다.
- 로직이 검증되면 같은 스크립트를 그대로 원격 실측 1회에 쓴다:
  - 이미 CI로 빌드되는 arm64 이미지(`ghcr.io/piker0925/devtoolbox-backend:latest`, `.github/workflows/deploy.yml`)를 SSH로 접속한 실제 VM에서 `docker pull`한다 — 새로 빌드하지 않는다.
  - 실제 운영 컨테이너(`devtoolbox-mysql`, `devtoolbox-backend`, 포트 8080/3306)와 완전히 분리된 별도 포트·별도 DB로 임시 컨테이너를 띄운다(103의 `local-benchmark` 프로파일 격리 원칙과 동일).
  - k6 자체는 로컬 Mac에서 실행하고 SSH 터널(`ssh -L`)로 원격 포트에 연결한다 — 새 인바운드 방화벽 규칙을 열지 않는다.
  - 측정 후 JFR 파일·raw 데이터를 회수하고 임시 컨테이너·DB를 정리한다.

### 왜 이 방식인가 — 대안 비교

| 대안 | 정확도 | 비고 |
|---|---|---|
| 로컬 `--cpus=2`만 | 낮음 | 코어 개수만 맞고 클록·IPC 차이는 못 잡음 |
| 로컬 + 실측 보정 계수(Mac·VM에서 동일 CPU-bound 작업을 각각 돌려 비율 측정 후 스케일링) | 중간 | 유효한 근사치지만, 이번엔 실제 VM 접근이 가능해 굳이 근사할 이유가 없음 |
| **실제 VM에서 격리 실행 (채택)** | 높음 | 하드웨어 차이 자체가 없음. 기존 CI/CD·arm64 이미지를 그대로 재사용해 추가 인프라가 필요 없음 |
| 103처럼 절대 수치를 스코프 밖에 둠 | 안전 | 167이 요구하는 캐파시티 서사(acceptance criteria)를 낼 수 없어 채택 안 함 |

이 인스턴스는 Always Free A1 한도의 절반만 쓰고 있고 리셰이프도 불가능한 유일한 배포 대상이지만, 실사용 트래픽이 없는 상태라 짧은 시간 격리된 벤치마크로 잠깐 점유하는 데는 실질적 리스크가 없다.

## 결과 — 알려진 제약

- 로컬↔원격 네트워크 지연이 k6가 재는 HTTP 왕복시간에 섞여 들어갈 수 있다. 종단간 완료 지연시간은 k6 `Trend`(폴링 감지)와 103처럼 `job` 테이블 타임스탬프 교차검증으로 보정한다 — 서버측 처리·대기 시간이 네트워크 왕복보다 지배적이라는 전제는 103에서 이미 확인됨.
- 원격 실측은 반복 비용(SSH 왕복, 이미지 pull, 정리)이 로컬보다 크므로, 스크립트 로직 검증이 끝난 뒤 **1회만** 실행하는 것을 원칙으로 한다 — 로직 버그가 있는 채로 원격에서 여러 번 재실행하지 않는다.
- 실제 운영 컨테이너·DB에는 영향을 주지 않는다(별도 포트·DB로 완전 격리). 이 전제가 깨지면(포트·DB 이름 충돌 등) 즉시 중단한다.
