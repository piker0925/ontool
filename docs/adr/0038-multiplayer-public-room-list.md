# ADR-0038 멀티플레이 방 참가 방식 — 코드 입력 대신 공개방 목록

## 상태

확정 (2026-07-31)

## 배경

193 파일럿(반응속도 대결)에서 확립한 멀티플레이 참가 방식은 "방 만들기(코드 발급) + 코드 입력해서 참가" 둘뿐이었다. 실사용 관점에서 코드를 다른 사람에게 전달해야 하는 절차 자체가 번거로움으로 지적됐다 — 친구를 초대하려면 코드를 채팅 등 별도 채널로 공유해야 진입이 가능했다.

비공개/공개 구분을 둔 절충안(공개로 연 방만 목록 노출)도 검토했으나, 이 프로젝트는 동시 접속자가 매우 적은 포트폴리오 성격이라(→ `game-plan.md`, 관측성 ADR-0036과 동일 전제) 방을 비공개로 만들 실익이 없고, 목록/코드 두 경로를 병행하면 구현·테스트 표면만 늘어난다.

## 결정

**모든 방을 공개방으로 통일하고, 참가는 코드 입력 대신 "대기중인 공개방 목록"에서 고르는 방식으로 교체한다.**

- `Room`에 `gameId` 필드를 추가한다(생성 시점에 저장) — 기존에는 `RoomRegistry`가 전역 `Map<code, Room>`으로만 관리해 방이 어느 게임 소속인지 몰랐다. 목록을 게임별로 걸러 보여주려면 이 정보가 필요하다.
- `RoomRegistry.listWaitingRooms(gameId)` — 같은 게임 + 시작 전 + 정원 미달인 방만 반환.
- `GET /api/v1/games/{gameId}/rooms` — 목록 조회 엔드포인트, `RoomSummaryResponse(code, participantCount, maxParticipants)` 반환. 참가자 닉네임 등 상세는 노출하지 않는다.
- 프론트 `BattleLobbyShell.vue`(11개 게임 로비가 공유하는 셸)의 "코드 입력" UI를 제거하고, 그 자리에 대기방 목록(빈 상태 포함)을 렌더링한다. 목록 항목 클릭 시 기존 `join(code)` 흐름을 그대로 재사용한다 — 방장이 자기 방 코드를 확인하는 대기실 화면(Phase 1)은 유지(디버깅·지원 용도로 무해).
- 목록 갱신은 SSE가 아니라 **폴링**(3초 간격, 로비 진입 중에만)으로 한다.
- 코드(`code`) 자체는 폐기하지 않는다 — 참가 API의 내부 식별자로는 계속 쓰되, 사용자에게 입력받는 UI만 없앤다.

### 왜 이 방식인가 — 대안 비교

| 대안 | 비고 |
|---|---|
| 코드 입력 유지 + 목록 병행(공개방 토글 옵션) | 편의성은 있으나 비공개 개념을 위한 필드·분기가 추가로 필요 — 동시접속이 적어 실익 대비 구현비용이 안 맞음 |
| **전부 공개방 + 목록만 (채택)** | 코드 개념은 내부적으로 유지되어 백엔드 변경이 최소화되고, 프론트는 공유 셸 한 곳만 고치면 됨 |
| 목록 실시간 갱신에 SSE 확장(`RoomBroadcaster`에 lobby 채널 추가) | 인프라는 재사용 가능하나 동시접속이 적어 폴링으로 충분 — 과설계 방지 |

## 결과 — 알려진 제약

- `RoomRegistry.create()` 시그니처가 `create(gameId)`로 바뀌었다 — 순수 함수 변경이라 마이그레이션 이슈는 없음(메모리 전용 상태).
- 목록은 3초 폴링이라 새로 열린 방이 화면에 반영되기까지 최대 3초 지연이 있을 수 있다. 로비 체류 시간이 짧아 문제되지 않는 것으로 판단.
- 방을 비공개로 만드는 기능은 없다 — 필요해지면 `Room`에 `isPublic` 필드를 추가하는 정도로 확장 가능(현재는 불필요 판단).
