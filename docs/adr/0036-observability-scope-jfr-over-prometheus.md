# ADR-0036 관측성 도구 선택 — JFR만 사용, Prometheus/Grafana/Loki 도입 안 함

## 상태

확정 (2026-07-26)

## 배경

v4 배치 완료 후 프로덕션 준비도를 재점검하는 과정에서, 실측 성능 수치가 없다는 점(103은 공정성 벤치마크지 처리량 벤치마크가 아님, → 167 부하테스트로 메움)과 별개로 **관측성이 전혀 없다는 점**이 확인됐다 — `application-prod.yaml`은 actuator `health`만 노출하고(`show-details: never`), 큐 깊이·GC·CPU 등 실행 중 시스템 상태를 볼 방법이 전무하다.

167(Heavy 큐 부하테스트, k6 breakpoint test)을 앞두고 "그때 병목을 눈으로 봐야 설득력 있는 스토리가 된다"는 이유로 Micrometer+Prometheus+Grafana 도입이 처음 검토됐다. 그릴링 과정에서 전제부터 재검토했다: 왜 필요한지, 어떤 지표가 필요한지, 어떤 도구로 수집하는지, 왜 그 도구인지, 대안은 없는지.

## 결정

**Prometheus·Grafana·Loki를 도입하지 않는다.** 대신:

- **JVM 레벨 병목(CPU·GC·스레드·락 경합) 진단은 JFR(Java Flight Recorder)만 쓴다.** JDK 내장이라 신규 의존성·인프라가 없고, prod에서도 기본 프로필 기준 ~1% 오버헤드로 상시 켜둘 수 있으며, 문제가 생긴 뒤에도 `jcmd JFR.dump`로 최근 구간을 즉시 뽑아낼 수 있다(사전에 녹화를 트리거해둘 필요가 없음). 시각화가 필요하면 JDK Mission Control(JMC)로 열어 타임라인 그래프를 보고, 필요시 스크린샷만 남긴다 — 상시 대시보드 서비스는 두지 않는다.
- **도메인 수치(큐 깊이 임계 도달 시점, 거부 시점)는 이미 있는 신호로 충분하다.** `AdmissionControl`이 이미 503(QUEUE_FULL)·507(STORAGE_FULL)을 명시적으로 구분해 응답하므로, k6가 이 상태코드를 집계하는 것만으로 "언제·왜 거부되기 시작했는지"가 나온다. 더 정밀한 시점이 필요하면 103 벤치마크와 동일하게 `job` 테이블을 직접 SELECT한다(`docs/benchmarks/103-heavy-queue-bench/README.md`). 결과는 그래프·대시보드가 아니라 **표 + 원본 데이터 파일 링크**로 남긴다 — 103이 이미 이 패턴으로 충분한 설득력을 보였다.
- 커스텀 Micrometer 게이지·Prometheus 포맷 노출·docker-compose Prometheus/Grafana 서비스는 **local·prod 어느 쪽에도 추가하지 않는다.**

### 왜 Prometheus/Grafana가 아닌가

Prometheus의 고유 가치(장기 시계열 추세, PromQL 집계, 알림, 다중 인스턴스 집계)를 이 프로젝트 조건과 대조하면:

| Prometheus 고유 가치 | 이 프로젝트에 실재하는가 |
|---|---|
| 여러 회차·장기간 추세 비교 | 불필요 — 103 패턴(전/후 비교표)으로 이미 충분히 해결됨 |
| PromQL 임계 집계 | 1회성 breakpoint 테스트엔 과함 |
| 알림(threshold alert) | on-call 없음, 받을 사람이 없음 |
| 다중 인스턴스 집계 | 단일 VM, 단일 인스턴스 — 해당 없음 |
| 장기 추세(디스크 사용량 등)로 선제 대응 | `AdmissionControl`이 매 요청마다 파일시스템을 실시간 재확인하고, 정리 스케줄러가 멱등이라 스스로 처리함 — 사람이 추세를 지켜보다 개입할 상황이 설계상 없음 |

즉 Prometheus가 실제로 잘하는 일 중 이 프로젝트에 진짜 필요한 게 없다. 남는 건 "라이브 대시보드가 보기 좋다"는 시각적 편의뿐인데, 이는 기술적 필요가 아니라 취향에 가깝다. 그 정도 이유로 2코어 VM에 상시 서비스 두 개(Prometheus+Grafana)를 얹는 건 분산 락을 넣지 않기로 한 것과 같은 이유로 배제한다 — **자연스러운 필요가 없는 인프라는 넣지 않는다.**

Loki는 더 근거가 약하다. Loki의 핵심 가치는 "여러 인스턴스에 흩어진 로그를 한곳에서 검색"인데, 단일 VM은 로그가 애초에 한 곳에만 있어 `ssh` + `grep`으로 충분하다.

GA4는 별개 축이라 이 판단에 영향을 주지 않는다 — GA4는 프론트엔드 제품/사용자 분석(누가 어떤 기능을 썼는지)이고, 여기서 다루는 건 백엔드 시스템 관측(큐·GC·CPU)이다. 서로 대체하지 않는다.

## 결과 — 알려진 제약

- **장기 추세 관측 공백을 의도적으로 남긴다.** 디스크 사용량이나 큐 깊이가 몇 주에 걸쳐 서서히 나빠지는 패턴은 이 구성으로 못 잡는다. 지금은 실사용 트래픽이 없어 관찰할 추세 자체가 없으므로 문제가 되지 않는다. **재고 시점**: 실사용 트래픽이 붙어 지속적인 부하 패턴이 생기면, 그때 Micrometer+Prometheus 재도입을 검토한다 — 지금은 그 조건이 성립하지 않는다.
- 167(부하테스트) 결과 문서는 JFR 스크린샷(선택) + k6 상태코드 집계 + `job` 테이블 조회 기반 표로 작성한다. 별도 그래프·대시보드 이미지는 만들지 않는다.
